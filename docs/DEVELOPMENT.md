# Development

## First-time setup

```bash
make setup && make up-build   # env file, self-signed SSL cert, build every image, start the stack
make migrate                  # alembic upgrade head — run after any model/migration change
make health                   # verify every container is healthy
```

Everything else is driven through the `Makefile` against `docker compose`; most targets `exec` into
already-running containers, so `make up`/`up-build` has to come first.

## Common commands

```bash
make logs-api / make logs-workers / make logs-nginx

make test                     # pytest tests/ -v         (inside the api container)
make test-unit                # tests/unit/ only
make test-integration         # tests/integration/       (needs the full stack running)
make test-coverage

make lint                     # ruff check app/ workers/  +  npm run lint (frontend)
make format                   # ruff format + isort (backend)  +  npm run format (frontend)
make type-check                # mypy app/  +  tsc --noEmit

make migrate-create MSG="add xyz table"   # alembic revision --autogenerate
make migrate-rollback
make db-shell                  # psql shell
make shell-api / make shell-worker

make workers-scale NUCLEI=6 DISCOVERY=4 PORT=3
# or: docker compose up -d --scale worker-nuclei=6 --no-recreate
```

Run one test directly:

```bash
docker compose exec api pytest tests/unit/test_risk_engine.py -v
docker compose exec api pytest tests/unit/test_risk_engine.py::test_grade_boundaries -v
```

There is no `conftest.py`/`pytest.ini` — tests `import app.*` directly, so they must run with
`backend/` as the working directory, which `docker compose exec api` already provides.

Frontend runs locally, not containerized for dev (the container build is `production`-only, no hot
reload — see [FRONTEND.md](./FRONTEND.md)):

```bash
cd frontend && npm install
npm run dev          # localhost:3000
npm run type-check   # tsc --noEmit
npm run lint
npm test             # jest --passWithNoTests (little/no coverage currently)
```

## Migrations

⚠️ **`alembic revision --autogenerate` in this repo currently picks up a large amount of pre-existing,
unrelated schema drift** across many tables that have nothing to do with whatever change you're making
(server-default/nullable mismatches accumulated over time, not something any single change caused).
**Do not blindly ship an autogenerated migration.** Read the generated file, strip it down to only the
`op.*` calls relevant to your actual change, and hand-write the rest if the tool's diff is noisy. See
`backend/app/db/migrations/versions/4ec377801f60_add_workspace_enabled_products.py` for the pattern:
minimal, hand-written, one column, explicit `server_default` for backfilling existing rows.

## Risk scoring formula

`backend/app/services/risk_engine.py`, tested in `backend/tests/unit/test_risk_engine.py`.

1. Findings currently `false_positive`, `resolved`, or `is_risk_accepted` are excluded entirely.
2. Every remaining finding maps to one of 9 categories (`FINDING_CATEGORY_MAP`; unmapped categories
   default to `misconfiguration`) and gets a severity-based raw penalty:

   | Severity | Penalty |
   |---|---|
   | critical | 25.0 |
   | high | 15.0 |
   | medium | 8.0 |
   | low | 3.0 |
   | info | 1.0 |

3. Each penalty is scaled by **exponential time decay**: `exp(-λ × days_old)`, `λ = RISK_DECAY_LAMBDA`
   (default `0.05`) → **half-life ≈ 14 days** (`ln(2)/0.05 ≈ 13.9`) — a finding open for a month
   contributes noticeably less than one discovered yesterday, without ever fully zeroing out.
4. Each penalty is also scaled by an **asset/org criticality multiplier** (`Asset.criticality` /
   `Organization.criticality`, 1–5): `{1: 0.70, 2: 0.85, 3: 1.00, 4: 1.15, 5: 1.30}` — criticality 3 (the
   schema default for both) is the neutral point, so a finding with no criticality signal scores
   exactly as it would have before this field existed.
5. Per category: `category_score = max(0, 100 - min(Σ decayed·weighted penalties, 100))` — capped at
   100 points of deduction so one category can't go negative or bleed into another's weight.
6. `overall_score = Σ(category_score × category_weight)`, weights (must sum to 1.0):

   | Category | Weight |
   |---|---|
   | Exposure Management | 18% |
   | Network Security | 15% |
   | Web Security | 15% |
   | TLS Security | 12% |
   | Patch Hygiene | 10% |
   | DNS Health | 10% |
   | Info Leakage | 8% |
   | Reputation | 7% |
   | Misconfiguration | 5% |

7. Letter grade: `≥90 A`, `≥75 B`, `≥60 C`, `≥40 D`, else `F`.

## Config

All settings are env-driven via `backend/app/core/config.py` (`pydantic-settings`, `Settings` class),
loaded once via `get_settings()`/`settings`. To add a new env var: add the field there (with a default
for non-prod), and if a *worker* needs it, also add it under that service's `environment:` block in
`docker-compose.yml` — workers read `os.getenv(...)` directly, they don't share the backend's pydantic
`Settings` object. `.env.example` documents the full set; keep it in sync.

## Gotchas (from real incidents — see `CHANGELOG.md` for the full stories)

- **`pg_insert(Model)` vs `pg_insert(Model.__table__)`** — SQLAlchemy 2.0 requires the latter for
  upserts in worker code; passing the ORM class directly breaks the bulk-persistence path.
- **Go tool binaries vs pip packages of the same name** — the pip `httpx` package installs a CLI at
  `/usr/local/bin/httpx` that can shadow the ProjectDiscovery Go `httpx` binary if `PATH` isn't ordered
  correctly. `workers/Dockerfile` prepends `/go/bin` to `PATH` for exactly this reason — don't reorder
  it.
- **Trailing slashes** — endpoint collection routes are `@router.get("")`, never `@router.get("/")`; a
  trailing slash 307-redirects, which breaks some clients/axios calls without `trailingSlash` config.
- **RabbitMQ topology drift** — three separate copies of the queue routing table exist in code and can
  disagree; see [PIPELINES.md](./PIPELINES.md#queue-topology).
- **Worker containers mount `backend/app` read-only** — editing a backend module used by workers takes
  effect on worker restart, no image rebuild; a new worker *file* or new dependency does need one.
- **Workers are long-running processes — editing a `.py` file on disk does not update an already-running
  worker's in-memory module.** `docker compose restart worker-X` is required before a code change takes
  effect. This produced multiple confusing false-negative test results across this project's history
  (a feature appearing to silently do nothing until the relevant worker was restarted) — always restart
  after a worker-code change, before concluding a test result either way.
- **`report.daily` has no consumer** — see [ARCHITECTURE.md's drift notes](./ARCHITECTURE.md#docs-vs-reality).
- **NGINX rate limiting on rapid sequential calls** — the `api` zone (200r/m, burst 50) trips on
  patterns like promoting hundreds of items one HTTP call at a time. The fix is a real bulk endpoint in
  one transaction (see `POST /bounty/programs/{id}/assets/promote-bulk`), not client-side pacing.
- **Frontend container has no hot reload** — `target: production` in `docker-compose.yml`; a `.tsx`
  change needs `docker compose build frontend && docker compose up -d --no-deps frontend` before it's
  visible, even though the dev-mode `npm run dev` workflow doesn't need this.
- **Migration autogenerate noise** — see [Migrations](#migrations) above.
- **NGINX regex static-asset location beats plain prefix locations** — `nginx.conf` has a
  `location ~* \.(js|css|png|...)$` block for long-cache static assets, and by NGINX's own matching
  rules a regex location always wins over a plain prefix location unless that prefix uses the `^~`
  modifier. Any new reverse-proxied service that serves its own `.js`/`.css` (Grafana, Prometheus, a
  future one) needs `location ^~ /whatever/`, not just `location /whatever/` — without it, every JS/CSS
  request for that service silently gets routed to the frontend upstream instead and 404s there
  (surfaced as Grafana's own "failed to load application files" screen / a blank Prometheus page — see
  `CHANGELOG.md`, 2026-07-23).
- **Grafana behind a subpath needs `GF_SERVER_SERVE_FROM_SUB_PATH=true` *and* no trailing slash on
  `proxy_pass`** — with the env var set, Grafana expects the `/grafana` prefix still present on the
  incoming request path; a trailing-slash `proxy_pass http://grafana:3000/;` strips that prefix before
  forwarding, and Grafana redirects back to `/grafana/` to "correct" it — an infinite redirect loop.
  `proxy_pass http://grafana:3000;` (no trailing slash) forwards the full path unchanged instead.
- **Prometheus's `/-/reload` (`--web.enable-lifecycle`) didn't actually refresh the bind-mounted config
  in this environment** — editing `prometheus.yml` and hitting the reload endpoint returned 200, but the
  running container kept reading stale content (confirmed via mismatched inode/mtime between the host
  file and what the container saw). A full `docker compose restart prometheus` did pick up the change.
  Worth trying a full restart first if a config edit doesn't seem to take effect, rather than assuming
  the edit itself was wrong.
- **RabbitMQ's Prometheus plugin has no per-queue labels by default** — `rabbitmq_queue_messages` (and
  similar) only exposes one cluster-wide aggregate unless `prometheus.return_per_object_metrics = true`
  is set in `rabbitmq.conf` (~24 queues here, so the added series count is small). Without it, any
  dashboard panel expecting a `queue`/`vhost` label (e.g. `legendFormat: "{{queue}}"`) silently renders
  nothing, indistinguishable from a broken query.

## Registration → workspace → product entitlement (for anyone extending auth)

A self-serve registration **always** creates a brand-new `Workspace` — there is no "join an existing
workspace" flow in code today (`RegisterRequest.invite_token` exists in the schema but is currently
unread/dead in `register()`). This is why product entitlement (`Workspace.enabled_products`) is chosen
once, at registration, rather than being a per-user setting layered on later: one registration, one new
workspace, one product choice. See [API_REFERENCE.md](./API_REFERENCE.md#product-entitlement) for the
enforcement side and [FRONTEND.md](./FRONTEND.md#two-dashboards-one-codebase) for the UI side.
